# 技术选型 Skill：AI 辅助的最小技术栈开发

## 1. 核心目标

为日常开发中的辅助工具、内部工具、自动化脚本、轻量客户端和数据处理程序，选择成本最低、风险可控、交付可靠的技术方案。

核心原则：

**AI 降低了编码成本，因此技术选型应更加关注成熟度、交付成本、运行依赖、可靠性和长期维护成本。**

不要因为某项技术流行、功能强大或 AI 能够生成代码，就默认采用它。

每次技术选型都应回答一个问题：

> 在满足实际需求的前提下，哪种成熟技术能够以最少的复杂度，可靠地完成开发、测试、部署和维护？

## 2. 适用范围

遇到以下任务时，使用本 Skill：

- 内部小工具、辅助程序、一次性工具。
- Windows 桌面客户端、系统托盘程序。
- 命令行工具、批处理、自动化脚本。
- 文件处理、数据转换、导入导出。
- 局域网通信、离线数据暂存、断网恢复后补传。
- 需要打包后分发到其他机器运行的程序。
- 为现有系统补充非核心业务能力。
- 新项目的语言、框架、数据库、部署方式和架构选型。

如果用户已经明确指定技术栈，原则上遵从。只有当指定技术无法满足关键需求、存在明显风险或成本显著不合理时，才提出替代方案。

## 3. 基本原则

### 3.1 先解决问题，再选择技术

首先理解需求，不要一开始就罗列框架。

需要识别：

- 实际要解决的问题。
- 输入、输出和关键业务规则。
- 目标操作系统、运行环境和硬件条件。
- 是否需要 GUI、后台运行、系统托盘或开机启动。
- 是否需要离线运行、持久化存储和故障恢复。
- 如何安装、升级、卸载和排查问题。
- 如何验证功能正确。

只有缺失信息会实质性改变技术选型时，才向用户询问。其他情况可以明确合理假设并继续，不要用冗长的需求问卷阻塞开发。

### 3.2 优先采用最小技术栈

技术选择优先级：

1. 操作系统已有能力。
2. 仓库和现有项目已有的成熟技术。
3. 团队熟悉、文档完善、依赖少的通用技术。
4. 能明显降低总成本的新框架或新组件。

不要为一个简单工具默认引入：

- 微服务架构。
- 消息队列和复杂中间件。
- 容器平台或额外的常驻服务。
- 大型前端运行时。
- 复杂插件系统。
- 多层抽象和不必要的设计模式。
- 仅为未来可能出现的需求而提前建设的基础设施。

### 3.3 计算总成本，而不是只看开发速度

至少考虑：

- 编码和测试成本。
- 依赖安装和环境配置成本。
- 部署、升级、卸载和回滚成本。
- 运行资源占用。
- 故障排查和恢复成本。
- 后续修改和人员交接成本。

代码少不一定意味着成本低，单文件可执行程序也不自动代表零依赖、高可靠或易维护。

### 3.4 可靠性来自设计和验证

AI 生成代码、编译成功或演示成功，都不能单独证明软件可靠。

涉及数据持久化、网络通信、业务状态和异常恢复时，必须设计明确的失败处理，并通过测试验证。

### 3.5 不随意改变现有环境

- 优先沿用仓库现有的语言、SDK、编译器和构建工具。
- 不擅自修改全局环境变量、JDK、Maven 配置或生产环境。
- 不无故升级依赖或重构无关代码。
- 不猜测仓库中已有的文件、模块和依赖，先检查实际情况。
- 涉及破坏性操作、生产部署、数据迁移或额外费用时，先取得用户授权。

## 4. 标准技术选型流程

### 第一步：识别程序类型

根据需求确定主要类型，可以多选：

- CLI：命令行、批处理、自动化脚本。
- Desktop：桌面窗口、表单、系统托盘。
- Background：后台任务、系统服务、定时任务。
- Web：浏览器页面或 Web 服务。
- Data：文件处理、数据转换、导入导出。
- Integration：API 调用、局域网系统集成。
- Offline-first：断网可用、恢复后同步。
- Hardware：串口、USB、设备控制、专用驱动。

### 第二步：确定硬性约束

优先确认会改变选型的条件：

- 目标操作系统和 CPU 架构。
- 是否可以安装运行时、是否拥有管理员权限。
- 是否要求单文件分发或标准安装包。
- GUI 的复杂程度。
- 是否需要跨平台。
- 是否有离线、数据一致性、实时性要求。
- 是否需要复用已有代码、接口或数据模型。
- 是否存在安全、网络、存储或合规限制。
- 谁负责后续维护。

硬性约束优先于加权评分。无法满足关键约束的技术，不进入最终候选。

### 第三步：检查现有资产

在引入新技术之前，检查：

- 仓库当前使用的语言和框架。
- 已有的公共模块、SDK、数据模型和 API。
- 现有构建、测试和发布脚本。
- 目标机器已有的运行环境。
- 是否存在可以直接复用的系统功能或成熟库。

优先复用现有资产。只有复用会造成明显的兼容性、复杂度或安全问题时，才考虑更换技术。

### 第四步：提出少量候选

通常比较 2～3 个候选即可。

每个候选必须说明：

- 技术栈。
- 如何实现当前需求。
- 主要依赖和部署形式。
- 优点、缺点和风险。
- 开发、交付和维护成本。

不要为了显得全面而列出十几种技术。没有实际收益的方案不必纳入比较。

### 第五步：评估候选方案

先排除不满足硬性约束的方案，再使用以下默认权重评估：

| 维度 | 权重 | 判断标准 |
|---|---:|---|
| 需求匹配与可靠性 | 25% | 是否满足核心需求，能否测试和恢复 |
| 部署与运行依赖 | 20% | 安装、升级、运行时、权限和分发难度 |
| 全生命周期成本 | 20% | 开发、测试、维护和排障成本 |
| 成熟度与可维护性 | 15% | 文档、生态、稳定性和接手难度 |
| 开发效率与 AI 适配 | 10% | 是否容易实现、测试和调试 |
| 性能与资源占用 | 10% | CPU、内存、磁盘和启动速度是否满足要求 |

权重可以按项目调整，但必须解释调整原因。

不要伪造精确评分。证据不足时使用定性比较，并说明关键不确定性。

### 第六步：形成结论

选型结论应包含：

1. 首选技术栈。
2. 选择原因。
3. 放弃其他方案的原因。
4. 主要风险和需要验证的事项。
5. 构建、打包、部署和维护方式。
6. 下一步最小可执行动作。

如果用户要求直接开发，应简要说明关键选型理由后立即进入实施，不要停留在技术比较阶段。

## 5. 默认技术栈

以下是默认候选，而不是强制规定。最终选择必须结合目标环境、已有代码、团队能力和真实需求。

### 5.1 Windows 桌面客户端

**默认优先评估：C# + .NET + WinForms。**

适合：

- 简单窗口和表单。
- 内部业务客户端。
- 系统托盘程序。
- 文件处理和本地数据管理。
- Windows API 和局域网通信。
- 需要打包后交付给普通用户安装的工具。

其他情况：

- 复杂桌面交互：评估 WPF。
- 需要深度复用 C/C++ 库、硬件接口或明确要求底层控制：评估 C++。
- 需要跨平台原生 GUI，且 Qt 的能力和依赖合理：评估 Qt/C++。
- 需要丰富 Web 界面时，才评估 Tauri、Electron 等方案。

注意：

- .NET 自包含发布可以减少目标机器的运行时前置条件，但会增加发布体积。
- C++ 不等于零依赖；运行库、GUI 框架和插件仍需处理。
- 不要仅凭理论性能选择 C++。如果瓶颈并非 CPU 性能，开发和维护成本可能更重要。

### 5.2 命令行工具与自动化

**默认优先评估：PowerShell、Go、现有语言。**

- Windows 系统管理、一次性自动化：优先考虑 PowerShell 或系统已有命令。
- 独立分发、跨平台、文件处理和网络工具：优先评估 Go。
- 依赖数据分析库或已有 Python 环境：可以使用 Python。
- 需要复用 Java 业务逻辑、SDK 或既有工程体系：继续使用 Java。

不要为了生成单个可执行文件，就强行把已有成熟项目换成另一种语言。

### 5.3 后台服务和网络程序

**默认优先评估：Go、C# Worker Service、现有 Java 技术栈。**

- 轻量、独立、容易分发的网络工具：评估 Go。
- Windows 服务、Windows API 集成：评估 .NET Worker Service。
- 与现有 Spring Boot 项目共享业务逻辑：优先使用 Java/Spring。
- 需要长期运行的服务，应考虑日志、健康检查、自动重启、配置管理和升级策略。

只有确实需要独立部署、故障隔离、弹性扩展或明确的团队运营能力时，才引入新的服务边界和基础设施。

### 5.4 浏览器与 Web

- 需求本身发生在浏览器内时，优先考虑现有 Web 系统和浏览器原生能力。
- 需要离线时，评估 Service Worker、IndexedDB、PWA 等方案。
- 不要假设浏览器断网后仍然能够访问部署在局域网服务器上的动态页面或 API。
- 如果需求涉及本地硬件、特殊权限、长期后台运行或复杂离线能力，再评估独立客户端。

### 5.5 本地存储

根据数据特点选择：

- 简单配置：配置文件。
- 可重新生成的临时数据：普通文件。
- 需要查询、事务、断网暂存、任务状态和恢复同步：优先评估 SQLite。
- 多进程并发、高并发写入、集中共享或复杂权限：重新评估存储方案。

不要仅因为“数据将来可能增长”就默认引入 MySQL、PostgreSQL、Redis 或消息队列。

## 6. 离线暂存和网络恢复补传

凡是涉及断网采集、离线队列或恢复后同步，必须检查以下事项。

### 6.1 数据可靠性

- 数据成功持久化后，才向用户确认保存成功。
- 不把内存作为唯一的数据存储。
- 每条记录具有稳定且唯一的 ID 或幂等键。
- 程序崩溃或机器重启后，未完成的数据仍可恢复。
- 明确本地数据目录、备份方式、清理规则和磁盘空间不足时的行为。

### 6.2 同步正确性

- 明确区分待同步、同步中、已确认、失败和需人工处理等状态。
- 请求超时不代表服务端一定没有处理。
- 重试必须配合服务端幂等机制，避免重复入账。
- 服务端应通过唯一约束或等效机制保证重复请求不会重复产生业务结果。
- 只在获得可信的服务端确认后，将记录标记为已同步。
- 网络恢复不等于服务端可用；必须通过实际请求及响应判断。

### 6.3 重试和故障恢复

- 使用有上限或带退避的重试策略。
- 避免网络恢复后大量记录同时重试造成请求风暴。
- 记录失败原因、尝试次数和最后一次同步时间。
- 支持程序重启后继续处理未完成任务。
- 设计必要的人工重试、导出和恢复手段。

### 6.4 必须测试的故障场景

至少验证：

- 网络断开和恢复。
- 服务端不可用或返回错误。
- 请求超时，但服务端实际上已经入库。
- 同一记录重复提交。
- 程序在保存或同步过程中被强制关闭。
- 机器重启后恢复。
- 本地数据库或文件读写失败。
- 磁盘空间不足。
- 多窗口或多进程同时操作。

**离线补传的核心不是检测网络，而是确保数据持久化、同步可恢复、重复提交不会造成错误。**

## 7. 依赖与架构约束

每增加一个依赖，都要回答：

1. 它解决了什么实际问题？
2. 不引入它是否可以用更简单的方式实现？
3. 它会增加多少部署和维护成本？
4. 它是否引入新的故障点或安全风险？

其他要求：

- 优先选择维护状态良好、文档可靠、许可证清晰的依赖。
- 锁定依赖版本，避免无必要的自动升级。
- 优先复用成熟组件，但不为很少使用的功能引入庞大依赖。
- 优先使用简单的模块化结构。
- 不为未来可能出现的需求提前构建复杂抽象。
- 不将关键可靠性建立在不可控的在线服务或未经验证的组件上。
- 涉及版本、许可证、支持期限或安全公告时，应查证官方资料，不得凭印象断言。

## 8. 打包、安装与交付

项目开始时就应考虑交付，不要等代码写完才研究如何安装。

必须明确：

- 目标操作系统、CPU 架构和最低系统版本。
- 构建和发布命令。
- 是否依赖外部运行时、DLL、系统组件或环境变量。
- 配置、数据库和日志的存放位置。
- 安装、升级、卸载和回滚方式。
- 程序版本和依赖版本。
- 是否需要管理员权限、代码签名或防火墙规则。
- 如何在干净的目标环境中验证安装。

优先选择可重复构建、可自动测试、容易诊断和容易回滚的交付方式。

不得把开发机上运行成功当作目标机器部署成功。

## 9. 测试和验收

测试规模应与风险匹配，不要求每个小工具都引入庞大的测试体系，但关键行为必须经过验证。

最低检查：

- 正常流程。
- 无效输入和边界值。
- 依赖不可用、超时和异常返回。
- 文件或数据库读写失败。
- 重启后的状态恢复（如适用）。
- 安装和启动验证。
- 日志能否定位问题。
- 关键数据是否可能丢失、重复或被覆盖。

涉及生产数据、数据一致性、权限或安全的功能，应提高测试标准，并尽可能通过自动化测试或故障注入进行验证。

交付时明确区分：

- 已实际验证。
- 尚未验证。
- 需要用户在目标环境验证。

不得仅根据编译成功、静态检查通过或 AI 自我审查就宣称程序可靠。

## 10. AI Agent 执行规范

Agent 必须：

- 先检查仓库说明、代码、依赖和构建方式。
- 区分事实、假设和未知信息。
- 优先给出明确结论和关键取舍。
- 先完成最小可验证版本，再根据测试结果迭代。
- 出现故障时优先分析根因，避免用连续临时补丁掩盖结构问题。
- 提供实际执行过的构建和测试命令及结果。
- 测试无法执行时，明确说明原因和未验证内容。
- 不随意修改与当前需求无关的文件和配置。

Agent 不得：

- 因为熟悉某项技术就默认选择它。
- 为了展示能力而引入不必要的框架或架构。
- 编造性能数据、兼容性、许可证或维护状态。
- 声称“绝对稳定”“零依赖”或“保证不丢数据”，除非有明确且可验证的限定条件。
- 把未经验证的示例代码冒充完整交付。
- 未经授权执行破坏性操作、生产部署或会产生费用的操作。

## 11. 标准输出格式

技术选型时，使用以下结构。简单任务可以缩短，但应保留关键结论。

### 结论
- 首选方案：
- 适用范围：

### 选择理由
- 需求匹配：
- 部署和依赖：
- 总成本：
- 可靠性：

### 主要取舍与风险
- 为什么不选其他方案：
- 哪些事项需要验证：

### 交付方式
- 构建与打包：
- 配置、数据与日志：
- 测试、升级与回滚：

### 下一步
- 一个最小、明确、可执行的动作。

如果用户只要求直接开发，不要机械输出完整报告。简短说明关键选型理由，然后开始实施。

## 12. 最终决策原则

当多个方案都满足硬性需求时，优先选择：

1. 能复用现有代码和工具链的方案。
2. 依赖少、部署简单、可重复构建的方案。
3. 数据状态清楚、异常容易排查的方案。
4. 容易测试、维护、交接和回滚的方案。
5. 全生命周期成本更低的方案。

不要追求所有项目只使用一种语言。

真正的目标是：

**常见需求有默认方案，特殊需求有明确例外，每个工具都能以可控成本交付，并通过测试证明关键行为可靠。**
